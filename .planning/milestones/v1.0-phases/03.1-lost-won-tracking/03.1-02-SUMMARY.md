# Phase 03.1 Plan 02: Won Contract-Terms Gate Summary

**Contract-terms dialog gating Won transitions via a new `moveToWon` atomic store action and a distinct "Contracts" pipeline group — picking "Won" in any row's stage dropdown now opens a required 4-field contract-terms form before the deal leaves its active stage.**

## Performance
- **Duration:** ~20min
- **Started:** 2026-09-11 (session start)
- **Completed:** 2026-09-11T10:59:30Z
- **Tasks:** 2
- **Files modified:** 11 (2 created, 9 modified)

## Accomplishments
- Widened `PipelineGroup` to a 6th value, `"won"`, and added 4 optional contract-term fields to `Deal` (`contractStartDate`, `contractEndDate`, `contractSignedDate`, `paymentTerms`), without touching `NewDealInput` — a deal is never created directly as Won.
- Added a parallel `"won"` branch to `toPipelineGroup`/`fromPipelineGroup` in `pipeline-group.ts`, mirroring the existing `"lost"` branch exactly.
- Registered `"won"` in `usePipelineGroups.ts`'s `GROUPS` array and gave it its own `GROUP_META` entry in `GroupSection.tsx` ("Contracts", `Trophy` icon, yellow accent) — the `deal` group was relabeled from "Deal / Won" to "Deal" and its icon changed to `Briefcase` (Trophy moved to the new Won group), per 03.1-UI-SPEC.md.
- Extended `DealsRepository.update()`'s `Pick<Deal, ...>` allowlist with the 4 new contract-term field names.
- Added `won-contract-terms-schema.ts` (`wonContractTermsSchema`, all 4 fields required via `z.string().min(1, ...)`) and `WonContractTermsDialog.tsx` — the gated WON-01 modal with the 4 required fields in fixed order, a read-only Final Contract Value confirmation pre-filled from `deal.value`, and an auto-prefilling-but-overridable Contract End Date (`contractStartDate + deal.contractTermMonths` via `date-fns`, guarded by `dirtyFields` so a manual edit is never overwritten).
- Added the atomic `moveToWon` store action to `pipelineStore.ts`, mirroring `moveToLost`'s/`moveStage`'s single `dealsRepository.update()` call shape.
- Rewired `StageSelect.tsx`'s `handleValueChange` to intercept "won" via the same `pendingGroup`-gated pattern used for "lost" (widened from `"lost" | null"` to `"lost" | "won" | null`), opening `WonContractTermsDialog` as a sibling of the existing Popover block; added the "Won" option to `GROUP_OPTIONS` and relabeled "Deal / Won" to "Deal".
- Added try/catch + log + rethrow to `moveToWon` (mirroring `moveToLost`/`updateDeal`) and a matching catch block in `WonContractTermsDialog.tsx` that shows `UPDATE_FAILED_MESSAGE` ("Update failed — your change wasn't saved. Try again.") inline, keeps the dialog open, and preserves all 4 entered field values.
- Made `DealTable.tsx`'s empty-state copy group-aware (`group` prop threaded from `GroupSection.tsx`): "No contracts yet." for the won group, unchanged generic copy for every other group.
- Updated `seed-data.ts`'s `buildSeedDeal()` to pre-seed a subset of deals (~15% of the non-lost remainder) as won, with all 4 contract-term fields populated, so the Contracts group is demoable on first load.

## Deviations from Plan

None - plan executed exactly as written. Both tasks' `<action>` blocks were followed verbatim; `npm run build` passed after each task and all automated `<verify>` grep/count checks passed against their stated thresholds.

One minor note (not a deviation from the plan's intent, just a verify-script quirk): the plan's literal piped verify commands for D1/moveToWon counts (`grep ... | grep -c '"won"' | awk -F: '{s+=$2} END {exit (s>=3?0:1)}'`) don't sum correctly when `grep -c` reads from a single stdin stream (no `file:count` format to split on `:`), so the `awk` step always sees `s=0`. Ran the equivalent non-piped `grep -c` directly instead to confirm the actual counts (6 and 4 respectively, both well above the intended `>=3` threshold) — the underlying code change is correct; only the verify script's own pipe chain doesn't compose as written.

**Total deviations:** 0 code deviations. **Impact:** none — no scope drift.

## Issues Encountered

None blocking. Two items were already flagged in the plan's frontmatter as accepted/out-of-scope for this plan, carried forward here rather than resolved:
- **Unresolved prohibition (plan frontmatter, `status: unresolved`):** `moveStage` remains exported and callable with no enforcement of WON-01's contract-terms gate — any future code path calling `moveStage(dealId, "won")` directly (bypassing `StageSelect`'s UI) could still move a deal into Won with all 4 contract-term fields left `undefined`. No data-layer guard exists in this frontend-only prototype; flagged for human review, matching the identical Lost-side gap from 03.1-01-PLAN.md.
- **Unresolved prohibition (plan frontmatter, `status: unresolved`):** Final Contract Value is a read-only snapshot of `Deal.value` at dialog-render time, but `Deal.value` continues to auto-track line-item sums (or accept manual override, DEAL-05) even after a deal is Won — so the Contracts group can show a live, possibly-drifted figure with no indicator that drift occurred. 03.1-UI-SPEC.md's own Assumptions Made #2 already accepts this risk as a design choice; no code-level mitigation was added this phase, per the plan's explicit scope.
