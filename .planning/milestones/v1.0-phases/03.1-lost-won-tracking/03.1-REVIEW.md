# Phase 3.1: Code Review Report

**Reviewed:** 2026-09-11
**Depth:** standard
**Files Reviewed:** 15
**Status:** issues_found

## Summary

Reviewed the Lost-reason gate (`LostReasonPopover` + `moveToLost`) and Won contract-terms gate
(`WonContractTermsDialog` + `moveToWon`) end to end, plus their shared plumbing
(`StageSelect`, `pipelineStore.ts`, `pipeline-group.ts`, `deals-repository.ts`, `deal.ts`,
`usePipelineGroups.ts`, `seed-data.ts`) and the two new shadcn primitives (`popover.tsx`,
`textarea.tsx`).

The two headline guarantees the task asked me to verify both hold up:
- **Atomicity:** `moveToLost` and `moveToWon` each call `dealsRepository.update` exactly once,
  inside a try/catch that rethrows (mirrors `updateDeal`). No double-call path found.
- **Dismiss = zero store actions:** Escape/click-away on the Lost popover (`StageSelect`'s
  `Popover onOpenChange`) and Escape/click-away/Cancel on the Won dialog
  (`WonContractTermsDialog.handleOpenChange`) both only clear local state — neither calls
  `moveToLost`/`moveToWon`/`moveStage`. Confirmed by reading every code path that can flip
  `pendingGroup`/`open`.
- **Error-state value retention:** both forms catch the rejection, set a local `error` string,
  and deliberately skip `form.reset`/`onClose` — entered values survive a failed submit in both
  components.

However, tracing what `moveToLost`/`moveToWon`/`moveStage` actually *write* to the `Deal` record
surfaced a real data-integrity gap (CR-01 below): none of the three actions clear the *other*
terminal state's fields when a deal transitions away from Lost or Won, so a deal can carry a
stale `lostReason` after being un-lost, or stale contract-term fields after being un-won — fully
reachable through the already-shipped `StageSelect` dropdown. A second, independent bug was found
in the new Won seed data's `contractEndDate` formula (CR-02). Three warnings and three info-level
items are also listed below.

## Critical Issues

### CR-01: Lost/Won fields are never cleared when a deal transitions away from that outcome

**File:** `src/features/pipeline/store/pipelineStore.ts:47-92`
**Issue:** `moveToLost` sets `lostReason` but never clears the 4 contract-term fields; `moveToWon`
sets the 4 contract-term fields but never clears `lostReason`; and the generic `moveStage` (used
whenever `StageSelect`'s dropdown target is anything other than `"lost"`/`"won"`) clears neither.
This is reachable today with no code changes:

1. Mark a deal Lost (sets `lostReason`).
2. Reopen that same deal's stage dropdown and pick `"Prospect"` → `handleValueChange` takes the
   non-gated branch and calls `moveStage(dealId, "prospect")` directly.
3. The deal is now `outcome: "open"`, `pipelineStage: "prospect"` — **but `lostReason` is still
   set** on the record.

The same applies in the other direction for Won: move a Won deal (with 4 contract fields
populated) back to `"Deal"` via the same dropdown, and `contractStartDate`/`contractEndDate`/
`contractSignedDate`/`paymentTerms` all persist on what is now an active, open deal. A deal could
even be bounced Lost → Won without ever going through an "open" stage, leaving both a stale
`lostReason` *and* a freshly-set set of contract fields on the same record simultaneously.

`toPipelineGroup` happens to ignore these stale fields for grouping (it only reads
`outcome`/`pipelineStage`), so nothing currently renders incorrectly — but the stored `Deal`
record itself is wrong, and the project's own forecast page (explicitly slated for a later phase
per PROJECT.md) would have no way to distinguish "genuinely still-Won data" from "leftover data
from a prior Won episode" without this fix, since both look identical on the record.

**Fix:** Explicitly null out the opposing fields in all three actions, e.g.:
```ts
moveToLost: async (dealId, category, note) => {
  const current = get().deals.find((d) => d.id === dealId);
  const patch = {
    ...fromPipelineGroup("lost", current?.pipelineStage),
    lostReason: note ? `${category}: ${note}` : category,
    contractStartDate: undefined,
    contractEndDate: undefined,
    contractSignedDate: undefined,
    paymentTerms: undefined,
  };
  // ...unchanged
},

moveToWon: async (dealId, terms) => {
  const current = get().deals.find((d) => d.id === dealId);
  const patch = {
    ...fromPipelineGroup("won", current?.pipelineStage),
    ...terms,
    lostReason: undefined,
  };
  // ...unchanged
},

moveStage: async (dealId, group) => {
  const current = get().deals.find((d) => d.id === dealId);
  const patch = {
    ...fromPipelineGroup(group, current?.pipelineStage),
    lostReason: undefined,
    contractStartDate: undefined,
    contractEndDate: undefined,
    contractSignedDate: undefined,
    paymentTerms: undefined,
  };
  // ...unchanged
},
```

### CR-02: Seed data's `contractEndDate` is computed from "today", not from `contractStartDate`

**File:** `src/data/mock/seed-data.ts:73-77`
**Issue:**
```ts
contractStartDate: isWon ? faker.date.recent({ days: 60 }).toISOString().slice(0, 10) : undefined,
contractSignedDate: isWon ? faker.date.recent({ days: 90 }).toISOString().slice(0, 10) : undefined,
contractEndDate: isWon
  ? format(addMonths(new Date(), contractTermMonths), "yyyy-MM-dd")
  : undefined,
```
`contractEndDate` is anchored on `new Date()` (the actual current date when the app boots),
completely independent of the randomly generated `contractStartDate`. This contradicts the app's
own business rule, implemented correctly in `WonContractTermsDialog.tsx:58-62`:
`contractEndDate = addMonths(parseISO(contractStartDate), deal.contractTermMonths)`. A seeded Won
deal with, say, `contractStartDate` 45 days in the past and `contractTermMonths: 12` will show a
`contractEndDate` roughly `today + 12 months`, not `contractStartDate + 12 months` — off by up to
60 days and visibly inconsistent with the rule a user just saw demonstrated live in the dialog.

**Fix:** Anchor `contractEndDate` on the same `contractStartDate` value used above:
```ts
const contractStartDate = isWon ? faker.date.recent({ days: 60 }) : undefined;
// ...
contractStartDate: contractStartDate?.toISOString().slice(0, 10),
contractEndDate:
  isWon && contractStartDate
    ? format(addMonths(contractStartDate, contractTermMonths), "yyyy-MM-dd")
    : undefined,
```

## Warnings

### WR-01: `MockDealsRepository.update`'s patch type silently drifted out of sync with the `DealsRepository` interface

**File:** `src/data/deals-repository.ts:14-33` (interface widened this phase); implementation in
`src/data/mock/mock-deals-repository.ts:69-76` (not updated)
**Issue:** This phase's diff widens `DealsRepository.update`'s `patch` type to add
`contractStartDate`/`contractEndDate`/`contractSignedDate`/`paymentTerms` to the `Pick`. The only
implementation, `MockDealsRepository.update`, still declares the old, narrower `Pick` (missing all
4 new keys) and was not touched by this diff. `npx tsc --noEmit` reports no error because
TypeScript checks method parameters bivariantly (a known unsoundness), and at runtime
`{ ...this.deals[index], ...patch }` merges whatever keys are actually present regardless of the
declared type — so `moveToWon` happens to work correctly today purely by accident of both of
those facts, not because the implementation's own type signature honors the contract it claims to
implement. Any future change to `update()` that relies on its own declared parameter type (e.g.
validating/whitelisting patch keys instead of blindly spreading) would silently drop the 4
contract fields with zero compiler warning.
**Fix:** Update `MockDealsRepository.update`'s `Pick` list to match the interface exactly:
```ts
update(
  id: string,
  patch: Partial<
    Pick<
      Deal,
      | "pipelineStage" | "outcome" | "lostReason" | "name" | "value" | "owner" | "closeDate"
      | "lineItems" | "contractStartDate" | "contractEndDate" | "contractSignedDate" | "paymentTerms"
    >
  >,
): Promise<Deal> { /* unchanged body */ }
```

### WR-02: `LostReasonPopover`'s `useForm` omits `defaultValues`, unlike every other form in this codebase

**File:** `src/features/pipeline/components/LostReasonPopover.tsx:40-42`
**Issue:** `AddDealDialog.tsx`, `LineItemsTable.tsx`, and this phase's own `WonContractTermsDialog.tsx`
all pass `defaultValues` to `useForm`. `LostReasonPopover` does not, so `note`'s RHF field value
starts as `undefined` and becomes a string the moment the user types — `Textarea`'s underlying
`<textarea>` is a native controlled element, so this triggers React's "A component is changing an
uncontrolled input to be controlled" console warning every time the popover is used, and (because
the popover unmounts/remounts on each open via `{pendingGroup === "lost" && <LostReasonPopover .../>}`)
repeats on every reopen.
**Fix:**
```ts
const form = useForm<LostReasonFormValues>({
  resolver: zodResolver(lostReasonSchema),
  defaultValues: { category: undefined, note: "" },
});
```

### WR-03: `moveToLost`/`moveToWon`/`moveStage` have no guard against a stale `current` lookup racing a concurrent update

**File:** `src/features/pipeline/store/pipelineStore.ts:47-92`
**Issue:** All three actions do `const current = get().deals.find(...)` *before* the `await
dealsRepository.update(...)`, then merge the result back with `get().deals.map(...)` *after* the
await. If two stage-moves for the same deal are in flight concurrently (e.g. a double-click on
"Confirm Won" before the first request resolves, or — once the mock repository is swapped for a
real network call per this project's own stated swap-later architecture — any two overlapping
edits), the second call's `current` snapshot can be stale relative to the first call's result, and
whichever `update()` resolves last wins, silently discarding the other's patch. This compounds
CR-01: a race between `moveToLost` and `moveToWon` on the same deal could leave it with neither
action's intended final state. Note: the Lost/Won 03.1-UI-SPEC.md explicitly defers a
submit-in-flight/double-submit guard as a documented backstop, so this is flagged as a
contributing factor to CR-01 rather than a standalone defect to fix in isolation — worth
revisiting together when that backstop is addressed.
**Fix:** Lowest-risk mitigation: disable the submit button while `form.formState.isSubmitting` in
both `LostReasonPopover` and `WonContractTermsDialog`, consistent with this being a known,
documented gap rather than a silent one.

## Info

### IN-01: Whitespace-only `note` is persisted verbatim into `lostReason`

**File:** `src/features/pipeline/store/pipelineStore.ts:60`, `src/features/pipeline/components/lost-reason-schema.ts:13`
**Issue:** `note: z.string().optional()` has no `.trim()`/min-length-after-trim check, and
`moveToLost`'s `note ? `${category}: ${note}` : category` treats any non-empty string (including
`"   "`) as truthy. A user who types only spaces into the optional note field ends up with a
stored `lostReason` like `"Other:    "`.
**Fix:** `note: z.string().trim().optional()` in the schema, or `note?.trim() ? ... : category` at
the call site.

### IN-02: `category`'s "Select a reason" validation error is unreachable dead code

**File:** `src/features/pipeline/components/LostReasonPopover.tsx:80,95`
**Issue:** `form.handleSubmit` (and therefore the `category` resolver error) can only run once the
submit button is clicked, but that button is `disabled={!form.watch("category")}` — so by the time
a submit can fire, `category` is always already set, and Radix `Select` has no way to revert a
selection back to empty. `fieldState.invalid && <FieldError errors={[fieldState.error]} />` for
`category` can therefore never render through normal user interaction.
**Fix:** Either remove the dead branch, or — if defensive validation is wanted regardless of the
disabled-button gate — leave it as documented defensive code with a comment explaining it's
unreachable via the UI today.

### IN-03: Seeded `contractSignedDate` has no guaranteed chronological relationship to `contractStartDate`

**File:** `src/data/mock/seed-data.ts:73-74`
**Issue:** `contractStartDate` is `faker.date.recent({ days: 60 })` and `contractSignedDate` is an
independently-rolled `faker.date.recent({ days: 90 })` — nothing constrains `contractSignedDate`
to fall on or before `contractStartDate`, so seeded demo data can show a contract "signed" after
its own start date.
**Fix:** Derive `contractSignedDate` from `contractStartDate` (e.g. a few days earlier) rather than
an independent random draw, for plausible demo data.
