# Phase 3.1: Lost & Won Tracking - Context

**Gathered:** 2026-09-10
**Status:** Ready for planning

<domain>
## Phase Boundary

Users can mark a deal as lost (blocked until a reason is given) with the deal moving into a distinct Lost group, and can mark a deal as Won by completing a contract-terms form, with Won deals appearing as a distinct "contracts made so far" group. Covers LOST-01, LOST-02, PIPE-03, WON-01. Does NOT touch: Phase 3's deal-terms wizard fields (Prorata/Grace Period/Contract Term/Frequency/Currency — already captured at creation, untouched here), Phase 4's search/filter/sort/forecast page, or any of the MRR/ARR/Lifetime Contract Value/Customer Type/Confidence Level fields added via quick tasks this session (those live on `Deal` independently and aren't part of this phase's scope).

</domain>

<decisions>
## Implementation Decisions

### Lost-move gating mechanism
- **D-01:** Selecting "Lost" in the per-row `StageSelect` dropdown does NOT move the deal immediately. An inline popover anchored to the dropdown opens asking for the reason; the move (`moveStage`) only commits once the popover is submitted. — **Reversibility:** reversible — purely a UI interaction change around the existing `moveStage` call, no data model impact.
- **D-02:** The reason input inside that popover is a fixed selector (Price, Timing, Competitor, No Budget, Other) plus an optional free-text note field. `Deal.lostReason?: string` already exists (unused placeholder from Phase 1) — store the selected category there, or extend the field/shape as needed to also carry the optional note (planner's call on exact shape: e.g. `"Price"` vs `"Price: budget cut mid-quarter"` concatenated, or a structured `{ category, note }` — no constraint given on this specific storage detail).
- **D-03:** Reason list, verbatim: Price, Timing, Competitor, No Budget, Other.
- **D-04:** If the user dismisses the popover (click-away, Escape) without selecting a reason, the move is fully cancelled — the `StageSelect` dropdown reverts to showing the deal's actual current stage, and `moveStage` is never called. No partial/half-committed state.

### Claude's Discretion — significant, flagged for planner/researcher revisit
The user explicitly chose to skip discussing these three areas and proceed to context — **not** because they're low-stakes, but as a deliberate time-boxing choice. Both remaining areas materially shape the implementation; treat the defaults below as a starting point, not a locked decision, and feel free to raise them again at plan time if something doesn't sit right (same posture Phase 2's CONTEXT.md took with its Value-override decision).

- **Won-trigger & contract-terms form UI:** ROADMAP.md's success criterion #3 describes "clicking Next (instead of Save) replaces the modal's content in place with a contract terms form, rather than closing the modal" — but no such modal currently exists. Phase 2 removed the old detail drawer entirely in favor of inline table editing (`EditableCell`) and a chevron-expandable line-items sub-row; there is no "Edit Deal" modal today, only `AddDealDialog` (creation-only) and the per-row `StageSelect` dropdown (instant-commit, now gated for Lost per D-01/D-02). Recommended default, reasoning from existing patterns: reuse `StageSelect` as the Won trigger too (selecting "Won" from the same dropdown, consistent with how Lost now works) — but because Won requires capturing 5 fields (not 1-2 like Lost's reason), open a full modal (matching `AddDealDialog`'s existing modal pattern) rather than a popover. Treat ROADMAP's literal "Next/Save" wording as describing the *intent* (a terms-capture step gates completing the Won transition), not a literal existing "Save" button to replace — no such button exists in the current stage-move flow to swap out.
- **Contract-terms fields vs. Phase 3's deal-terms fields:** WON-01 wants contract start date, end date/term length, signed date, payment terms, and final contract value. Some of these sound related to fields Phase 3 already captured at deal creation (`contractTermMonths`, `frequency`) but are not obviously identical:
  - "end date/term length" — could reuse the existing `contractTermMonths` (a duration) to compute/pre-fill an end date, or could be a wholly new field. No constraint given; recommend deriving/pre-filling from `contractTermMonths` + a new start date where sensible, but confirm at plan time since "term length" in WON-01 might be intended as independent of Phase 3's deal-terms field.
  - "payment terms (e.g. billing frequency/net terms)" — "billing frequency" plausibly reuses the existing `frequency` field; "net terms" (e.g. Net 30) is a distinct concept not currently captured anywhere.
  - "final contract value" — `Deal.value` already exists, auto-tracks the sum of line items with manual-override support (Phase 2, DEAL-05). Recommend treating "final contract value" as a read-only confirmation of the deal's current `value` at Won time rather than introducing a second, potentially-diverging value field — but this needs explicit confirmation since WON-01's wording ("captures... final contract value") could also mean a fresh, independently-entered number.
- Exact new type/field names (e.g. `wonAt`, `contractStartDate`, `contractEndDate`, `contractSignedDate`, `paymentTerms`) — no constraint given; follow the existing flat-field-on-`Deal` convention (matching Phase 3's precedent) rather than a nested object.
- Whether the new "Won" group is a genuinely new `PipelineGroup` value (e.g. `"won"`) separate from `"deal"` — **not really a gray area, already strongly implied by existing code**: `DealOutcome` already includes `"won"` as a value (currently unused/unreachable — nothing in the UI sets it), and `toPipelineGroup()`'s current logic (`outcome === "lost" ? "lost" : pipelineStage`) only needs a parallel `outcome === "won" ? "won" : ...` branch plus a `"won"` member added to `PipelineGroup` to make PIPE-03's "distinct group" requirement fall out naturally from code that's already shaped for it. Flagging this as high-confidence, not a genuine open question.

</decisions>

## Existing Code Insights

### Reusable Assets
- `src/shared/types/deal.ts` — `DealOutcome` already has `"won"`; `Deal.lostReason?: string` already exists as an unused placeholder. Both were explicitly built in Phase 1 anticipating this phase.
- `src/features/pipeline/components/StageSelect.tsx` — existing per-row dropdown; extend its `onValueChange` handling to intercept `"lost"` (open reason popover before committing) and likely `"won"` (open contract-terms modal before committing) rather than calling `moveStage` unconditionally.
- `src/features/pipeline/components/add-deal-schema.ts` + `AddDealDialog.tsx` — established react-hook-form + zod + shadcn Dialog pattern; the Won contract-terms modal should follow the same conventions (two-generic `useForm` workaround for `z.coerce.number()`, `Field`/`FieldLabel`/`Controller` composition).
- `src/components/ui/select.tsx` — already used for the reason-category selector; check if `src/components/ui/popover.tsx` exists yet for D-01's inline popover, generate via shadcn CLI if not.
- `src/shared/utils/pipeline-group.ts` — `toPipelineGroup`/`fromPipelineGroup`, the single place the new Won-group derivation logic belongs (mirroring how `"lost"` is already handled).

### Established Patterns
- Stage/outcome separation: `PipelineStage` (funnel position) and `DealOutcome` (open/won/lost) are modeled as two independent concerns since Phase 1 specifically so this phase wouldn't require a data-model rework (`research/PITFALLS.md` Pitfall 3, referenced in 01-CONTEXT.md).
- Repository/store seam: all writes go through `usePipelineStore` actions (`moveStage`, `updateDeal`) which call the repository — no direct state mutation, no parallel write path.
- Value auto-track-with-manual-override (DEAL-05): `Deal.value` stays in sync with `sumLineItems(lineItems)` until a user-entered value diverges from the computed sum — relevant precedent for the "final contract value" Claude's Discretion item above.

### Integration Points
- `StageSelect` is the single entry point for all stage/outcome changes across the app (used in `DealTable.tsx`) — both new gates (Lost-reason popover, Won-terms modal) hook in here, not a new/parallel UI surface.
- Existing `03-REVIEW.md`/`01-REVIEW.md` open findings (unhandled repository-promise rejection on `addDeal`/`moveStage`, no double-submit guard) apply directly to this phase's new write paths too — worth building the fix in from the start per STATE.md's Blockers note, rather than repeating the gap a third time.
