## Summary

This phase extends an already-prepared data model rather than building new plumbing. `Deal.outcome` already includes `"won"` [VERIFIED: src/shared/types/deal.ts:15] `export type DealOutcome = "open" | "won" | "lost";`, and `Deal.lostReason?: string` [VERIFIED: src/shared/types/deal.ts:68] already exists — both were deliberately left in place by Phase 1 anticipating this phase (per the file's own doc comment). The single derivation point (`toPipelineGroup`/`fromPipelineGroup` in `src/shared/utils/pipeline-group.ts`) is exactly the place PIPE-03's "distinct Won group" falls out of a parallel branch to the existing "lost" branch — no architectural rework needed, confirming the CONTEXT.md's own read of the code.

The two new UI surfaces (Lost-reason popover, Won contract-terms modal) both hook into the single existing entry point for all stage/outcome changes, `StageSelect` [VERIFIED: src/features/pipeline/components/StageSelect.tsx:32-56], which today calls `moveStage` unconditionally on every selection. Radix's Popover primitive is already present in `node_modules` as a transitive dependency of the installed `radix-ui` meta-package (`@radix-ui/react-popover@1.1.23`, confirmed via direct `package.json` read) — no new npm install is needed; only a new `src/components/ui/popover.tsx` wrapper file, hand-written to match this repo's existing `dialog.tsx`/`select.tsx` convention (`import { X as XPrimitive } from "radix-ui"`, `cn` from the `"cn"` package). The Won contract-terms modal should reuse `AddDealDialog.tsx`'s exact 2-step-wizard-in-one-`Dialog` pattern (local `step` state, single `useForm`, step-conditional `FieldGroup`/`DialogFooter`) — this is a proven, already-shipped pattern in this exact codebase, not a new one to invent.

The one genuine architecture risk this research surfaces: `moveStage` and `updateDeal` are two separate, single-purpose store actions today, and neither's type signature accepts the new reason/contract-term fields alongside a stage/outcome change. Chaining two sequential store calls (move, then a follow-up patch) would violate D-04's "no partial/half-committed state" requirement — a render could occur between the two awaited calls showing a deal as lost-with-no-reason, or the second call could fail leaving an inconsistent record. The recommendation is two new, atomic, single-call store actions (`moveToLost`, `moveToWon`) that compute the full patch (`pipelineStage` + `outcome` + `lostReason`/contract fields) and call `dealsRepository.update()` exactly once — mirroring `moveStage`'s existing single-call shape.

**Primary recommendation:** Add `"won"` as a fifth `PipelineGroup` value with a parallel `toPipelineGroup`/`fromPipelineGroup` branch (mirroring `"lost"`); gate both Lost and Won selections in `StageSelect` behind new atomic store actions (`moveToLost`, `moveToWon`) that never call `moveStage`/`updateDeal` as a two-step sequence; build the Won contract-terms modal as a structural copy of `AddDealDialog.tsx`'s 2-step-wizard pattern; hand-write `popover.tsx` from the already-installed `@radix-ui/react-popover` primitive rather than assuming the shadcn CLI's default output matches this repo's `"radix-nova"` custom style.

### Pattern 1: Gated commit via intercepted `onValueChange` + cancel-reverts-silently
**What:** `StageSelect`'s `Select` stays a `value`-controlled component (already true today — `value={currentGroup}` [VERIFIED: src/features/pipeline/components/StageSelect.tsx:42]). When the user picks "lost" or "won", do NOT call `moveStage`; instead open the gating UI (popover/modal) anchored to that selection. Because `Select`'s `value` prop is still bound to `currentGroup` (derived from the store, unchanged until the write commits), simply not calling any store action on dismissal is sufficient for D-04's "reverts to actual current stage" — no manual revert code is needed, since the underlying `Deal.outcome`/`pipelineStage` never changed, so `currentGroup` (computed via `toPipelineGroup`) never changed, so the rendered `Select` snaps back to its bound value automatically once the popover/dialog closes.
**When to use:** Any dropdown selection that requires a follow-up confirmation step before the underlying state changes.
**Example:**
```typescript
// Source: pattern derived from src/features/pipeline/components/StageSelect.tsx:32-56 (read this session)
export function StageSelect({ dealId, currentGroup }: StageSelectProps) {
  const [pendingGroup, setPendingGroup] = useState<"lost" | "won" | null>(null);

  const handleValueChange = (group: PipelineGroup) => {
    if (group === "lost" || group === "won") {
      setPendingGroup(group); // opens LostReasonPopover / WonContractTermsDialog
      return; // moveStage is NOT called — commit happens only on submit
    }
    void usePipelineStore.getState().moveStage(dealId, group);
  };

  return (
    <div onClick={(e) => e.stopPropagation()}>
      <Select value={currentGroup} onValueChange={handleValueChange}>
        {/* ...unchanged... */}
      </Select>
      {pendingGroup === "lost" && (
        <LostReasonPopover dealId={dealId} onClose={() => setPendingGroup(null)} />
      )}
      {pendingGroup === "won" && (
        <WonContractTermsDialog dealId={dealId} open onOpenChange={() => setPendingGroup(null)} />
      )}
    </div>
  );
}
```

### Pattern 2: 2-step-wizard-in-one-modal (Won contract-terms)
**What:** `AddDealDialog.tsx` already implements exactly the interaction ROADMAP's success criterion #3 describes ("clicking Next... replaces the modal's content in place... rather than closing the modal") for a *different* transition (Add Deal, step 1 → step 2). Reuse the identical structural pattern: one `Dialog`, local `useState<1 | 2>` step tracking, one `useForm` instance spanning both steps, step-conditional `FieldGroup` bodies, step-conditional `DialogFooter` buttons.
**When to use:** The Won modal specifically — this is the closest possible analog in this exact codebase (not a generic React pattern, a literal sibling component to copy).
**Example:**
```typescript
// Source: structural analog of src/features/pipeline/components/AddDealDialog.tsx:105-134 (read this session)
export function WonContractTermsDialog({ dealId, open, onOpenChange }: Props) {
  const moveToWon = usePipelineStore((s) => s.moveToWon);
  const [step, setStep] = useState<"confirm" | "terms">("confirm");
  const form = useForm<WonTermsFormInput, unknown, WonTermsFormValues>({
    resolver: zodResolver(wonContractTermsSchema),

  const onSubmit = async (values: WonTermsFormValues) => {
    await moveToWon(dealId, values); // single atomic store call — see Pitfall 1
    form.reset(WON_DEFAULT_VALUES);
    setStep("confirm");
    onOpenChange(false);
  };

  return (
    <Dialog open={open} onOpenChange={onOpenChange}>
      <DialogContent className="sm:max-w-md">
        <DialogHeader><DialogTitle>Mark as Won</DialogTitle></DialogHeader>
        <form onSubmit={form.handleSubmit(onSubmit)}>

          {step === "terms" && <FieldGroup>{/* 5 Controller fields, same pattern as AddDealDialog step 2 */}</FieldGroup>}

            {step === "confirm" && (

      </DialogContent>

```

### Pattern 3: Parallel derivation branch (`toPipelineGroup`/`fromPipelineGroup`)
**What:** Add `"won"` to `PipelineGroup` and thread a symmetric branch through both derivation functions, exactly mirroring how `"lost"` is handled today.
**When to use:** This exact extension point — CONTEXT.md's own "Claude's Discretion" section already identifies this as the correct seam, confirmed correct by direct reading.
**Example:**
```typescript
// Source: src/shared/utils/pipeline-group.ts:9-31 (read this session, verbatim current code below), extended
// CURRENT (verbatim):
// export function toPipelineGroup(deal: Deal): PipelineGroup {
//   return deal.outcome === "lost" ? "lost" : deal.pipelineStage;
// }
export function toPipelineGroup(deal: Deal): PipelineGroup {
  if (deal.outcome === "won") return "won";
  if (deal.outcome === "lost") return "lost";
  return deal.pipelineStage;
}

// CURRENT fromPipelineGroup (verbatim):
// export function fromPipelineGroup(
//   group: PipelineGroup,
//   previousStage?: PipelineStage,
// ): { pipelineStage: PipelineStage; outcome: DealOutcome } {
//   if (group === "lost") {
//     return { pipelineStage: previousStage ?? "prospect", outcome: "lost" };
//   }
//   return { pipelineStage: group, outcome: "open" };
// }
export function fromPipelineGroup(
  group: PipelineGroup,
  previousStage?: PipelineStage,
): { pipelineStage: PipelineStage; outcome: DealOutcome } {
  if (group === "lost") {
    return { pipelineStage: previousStage ?? "prospect", outcome: "lost" };
  }
  if (group === "won") {
    return { pipelineStage: previousStage ?? "deal", outcome: "won" };
  }
  return { pipelineStage: group, outcome: "open" };
}
```
`GROUPS` [VERIFIED: src/features/pipeline/hooks/usePipelineGroups.ts:7] `export const GROUPS: PipelineGroup[] = ["prospect", "lead", "opportunity", "deal", "lost"];` needs `"won"` appended (recommend inserting before `"lost"`, i.e. `[..., "deal", "won", "lost"]`, so the "contracts made so far" list sits next to the active-deal stage it graduates from, with Lost remaining the trailing/terminal group).

### Anti-Patterns to Avoid
- **Two sequential store calls for one transition:** Calling `moveStage(dealId, "lost")` and then a separate `updateDeal(dealId, { lostReason })` violates D-04's atomicity requirement and this codebase's own precedent (`moveStage` already does pipelineStage+outcome in one `dealsRepository.update()` call [VERIFIED: src/features/pipeline/store/pipelineStore.ts:39-45]). Compute the full patch object first, call `update()` once.
- **Widening `updateDeal`'s Pick type to include `pipelineStage`/`outcome`:** `updateDeal`'s action type is deliberately narrower than the repository interface (`Partial<Pick<Deal, "name" | "value" | "owner" | "closeDate" | "lineItems">>` [VERIFIED: src/features/pipeline/store/pipelineStore.ts:12-15], vs. the repository's own `Pick<Deal, "pipelineStage" | "outcome" | "lostReason" | "name" | "value" | "owner" | "closeDate" | "lineItems">` [VERIFIED: src/data/deals-repository.ts:14-22]). Widening the store action would let any `EditableCell`-style caller set `pipelineStage`/`outcome` directly, bypassing `fromPipelineGroup`'s derivation invariant (e.g. setting `outcome: "won"` with a stale `pipelineStage`). Add dedicated `moveToLost`/`moveToWon` actions instead.
- **Letting `AddDealDialog`'s creation-time group selector offer "Won":** `NewDealInput.group: PipelineGroup` [VERIFIED: src/shared/types/deal.ts:103] currently allows `"lost"` at creation with zero reason gate (`AddDealDialog`'s `GROUP_OPTIONS` includes `"lost"` [VERIFIED: src/features/pipeline/components/AddDealDialog.tsx:29-35], and `MockDealsRepository.create()` never checks `lostReason` [VERIFIED: src/data/mock/mock-deals-repository.ts:37-67]). This pre-existing gap is out of this phase's scope per CONTEXT.md's Phase Boundary (which names only the per-row `StageSelect` dropdown, D-01), but adding `"won"` to `AddDealDialog`'s `GROUP_OPTIONS` too would create a brand-new way to bypass WON-01's contract-terms gate at creation time. **Recommendation: do not add `"won"` to `AddDealDialog`'s `GROUP_OPTIONS`** — leave it at its current 5 values; only `StageSelect`'s `GROUP_OPTIONS` grows to 6.

**Key insight:** This phase's biggest "don't hand-roll" risk isn't a missing library — it's re-deriving state-transition logic that's already centralized. `toPipelineGroup`/`fromPipelineGroup` is the single source of truth for group membership; any new code that computes a deal's display group by checking `deal.outcome`/`deal.pipelineStage` directly (instead of calling `toPipelineGroup`) duplicates logic that will drift the moment a sixth group is ever added.

## Common Pitfalls

### Pitfall 1: Non-atomic Lost/Won commit (two sequential store writes)
**What goes wrong:** A `moveStage(dealId, "lost")` call followed by a separate `updateDeal(dealId, { lostReason })` call creates a window where the deal is "lost" with no reason recorded, and if the second call rejects (repository failure), the deal is left in that inconsistent state permanently — visually in the Lost group but with a blank reason, contradicting LOST-01's "requires ... a reason ... before the move completes."
**Why it happens:** The existing `moveStage` action's signature (`(dealId, group) => Promise<void>`) doesn't accept extra fields, making "call moveStage then patch the reason" the path of least resistance if a developer doesn't design a combined action first.
**How to avoid:** Add `moveToLost(dealId, category, note?)` and `moveToWon(dealId, contractTerms)` as new store actions that build one complete patch object and call `dealsRepository.update()` exactly once — see Pattern 3 / Anti-Patterns above.
**Warning signs:** Any new store action or component code that calls two `dealsRepository`/`usePipelineStore` write methods in sequence for what the user experiences as one action.

### Pitfall 2: Popover/Dialog dismissal not distinguished from submission
**What goes wrong:** Radix `Popover`'s `onOpenChange(false)` fires for Escape, click-outside, AND a programmatic close after successful submit — if the same handler is used to both "cancel" and "clean up after submit," a race is possible where closing after a successful submit is misread as a cancel-without-reason, or vice versa.
**Why it happens:** `Popover`/`Dialog`'s `onOpenChange` is a single boolean callback with no built-in way to distinguish "why" it closed.
**How to avoid:** Follow `AddDealDialog.tsx`'s established pattern exactly: the submit handler (`onSubmit`) calls `onOpenChange(false)` explicitly after the async store call resolves [VERIFIED: src/features/pipeline/components/AddDealDialog.tsx:113-120]; the popover/dialog's own `onOpenChange` prop (wired to Escape/click-away) is a *separate* handler that does nothing except close the local pending-state (never calls the store). As long as the store-mutating call site is the only place that can flip `pendingGroup` back to `null` via `onOpenChange(false)`-after-submit vs. an untouched Radix-driven close doing the same, D-04's "no partial state" holds because no store call happens on the Radix-driven path at all.
**Warning signs:** Any code path where `onOpenChange` is wired directly to a store-mutating function.

### Pitfall 3: Repository `update()`'s `Pick<Deal, ...>` allowlist not extended for new fields
**What goes wrong:** `DealsRepository.update()`'s type signature is an explicit `Pick<Deal, "pipelineStage" | "outcome" | "lostReason" | "name" | "value" | "owner" | "closeDate" | "lineItems">` [VERIFIED: src/data/deals-repository.ts:14-22]. If new Won contract-term fields (`contractStartDate`, etc.) are added to `Deal` but not to this `Pick` list, TypeScript will reject any `moveToWon` action that tries to pass them in its patch — a compile-time error, not a silent bug, but one a planner/executor could miss if they only edit `deal.ts` and the mock repository without also touching `deals-repository.ts`'s interface.
**Why it happens:** The `Pick<Deal, ...>` allowlist exists in a file separate from `Deal`'s own definition, and `MockDealsRepository.update()`'s implementation does a generic `{ ...this.deals[index], ...patch }` merge [VERIFIED: src/data/mock/mock-deals-repository.ts:84] that would silently accept extra fields at runtime even if the interface weren't updated (were TypeScript not catching it) — the type is the only real guard here.
**How to avoid:** When adding new `Deal` fields for Won contract terms, update `DealsRepository.update()`'s `Pick<...>` list in the same task/commit as the `Deal` interface change.
**Warning signs:** A type error on the new `moveToWon` action calling `dealsRepository.update()` with fields not in the interface's allowlist.

### Pitfall 4: Seed data (`buildSeedDeal`) producing invalid `Deal` objects after adding required new fields
**What goes wrong:** `seed-data.ts`'s `buildSeedDeal()` [VERIFIED: src/data/mock/seed-data.ts:34-76] currently generates all `Deal` fields explicitly and comments that "no seed deal is ever generated as 'won' this phase" [VERIFIED: src/data/mock/seed-data.ts:36-38] `// ~15% of seed deals are marked lost; never generate "won" this phase — 01-RESEARCH.md Open Question 2 defers the explicit won-transition to Phase 3, so all non-lost deals (including "deal" stage) stay "open".`. If new Won-contract fields are added to `Deal` as **required** (non-optional) fields, every one of the 40 seed deals will fail to type-check unless `buildSeedDeal()` is also updated to supply them (even for deals that aren't won) — the same class of issue Phase 3's `03-PATTERNS.md` already had to solve for its 5 new required deal-terms fields.
**Why it happens:** `Deal` is a single flat interface; adding a required field affects every code path that constructs a `Deal`, not just the new Won-transition path.
**How to avoid:** Make the new contract-term fields **optional** (`contractStartDate?: string`, etc.) on `Deal` — they genuinely don't exist until a deal transitions to Won, unlike Phase 3's deal-terms fields which are required at creation for every deal regardless of stage. This also sidesteps needing to backfill 40 seed deals with meaningless contract data. If any seed deals should demonstrate the Won state for demo purposes, update `buildSeedDeal()` deliberately to occasionally generate `outcome: "won"` with populated contract fields, matching the existing lost-generation pattern (`isLost` at ~15% probability).
**Warning signs:** A TypeScript error across many/all seed-deal-consuming call sites after adding new required `Deal` fields.

### New atomic store actions
```typescript
// Pattern source: src/features/pipeline/store/pipelineStore.ts:39-45 (moveStage, read this session), adapted
moveToLost: async (dealId, category, note) => {
  const current = get().deals.find((d) => d.id === dealId);
  const patch = {
    ...fromPipelineGroup("lost", current?.pipelineStage),
    lostReason: note ? `${category}: ${note}` : category,
    // ^ or a structured shape — see Assumptions Log A1 for the tradeoff
  };
  const updated = await dealsRepository.update(dealId, patch);
  set({ deals: get().deals.map((d) => (d.id === dealId ? updated : d)) });
},

moveToWon: async (dealId, terms) => {
  const current = get().deals.find((d) => d.id === dealId);
  const patch = { ...fromPipelineGroup("won", current?.pipelineStage), ...terms };
  const updated = await dealsRepository.update(dealId, patch);
  set({ deals: get().deals.map((d) => (d.id === dealId ? updated : d)) });
},
```
Both mirror `moveStage`'s existing shape exactly [VERIFIED: src/features/pipeline/store/pipelineStore.ts:39-45] `moveStage: async (dealId, group) => { const current = get().deals.find((d) => d.id === dealId); const patch = fromPipelineGroup(group, current?.pipelineStage); const updated = await dealsRepository.update(dealId, patch); set({ deals: get().deals.map((d) => (d.id === dealId ? updated : d)) }); },` — one repository call, replace-by-id.

## Open Questions

1. **Does selecting "Won" in `StageSelect` open the terms form directly, or go through an intermediate confirm step first?**
   - What we know: ROADMAP's success criterion #3 describes clicking "Next" (not "Save") to reveal the terms form in place — implying at least one prior screen exists before the terms form.
   - What's unclear: Whether that prior screen is `StageSelect`'s own dropdown selection (i.e., picking "Won" IS the equivalent of clicking something that reveals "Next"), or whether a dedicated confirm screen is needed inside the new modal before showing the terms form.
   - Recommendation: Default to no intermediate confirm screen — treat picking "Won" in `StageSelect` as the trigger that directly opens the modal already showing the terms form, with the modal's own submit button as the sole "complete Won" action. This is simpler, matches D-01's precedent for Lost (picking "Lost" directly opens the reason popover, no confirm step), and still satisfies "clicking Next replaces content in place" if interpreted as describing the *general mechanic* (gated reveal-in-place) rather than requiring a literal two-click sequence. Flag for confirmation at plan time regardless (see Assumption A5).

2. **Should Lost-marking at deal-creation time (`AddDealDialog`'s existing `"lost"` group option) also be gated with a reason, for consistency with this phase's new StageSelect gate?**
   - What we know: CONTEXT.md's Phase Boundary explicitly scopes D-01's gate to "the per-row `StageSelect` dropdown" only; `AddDealDialog`'s creation-time Lost path is unmentioned and currently ungated.
   - What's unclear: Whether this is a deliberate scope boundary (leave as-is) or an oversight that should be closed in the same phase for consistency, since LOST-01's requirement text ("User can mark a deal as lost, which requires selecting or entering a reason before the move completes") doesn't explicitly exclude the creation-time path.
   - Recommendation: Treat as explicitly out of scope per CONTEXT.md's literal Phase Boundary wording — do not touch `AddDealDialog.tsx`'s Lost path this phase. If the user wants consistency, that's a natural quick-task follow-up, not a Phase 3.1 blocker.
