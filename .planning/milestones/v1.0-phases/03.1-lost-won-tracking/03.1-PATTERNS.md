export function WonContractTermsDialog({ dealId, open, onOpenChange }: Props) {
  const moveToWon = usePipelineStore((s) => s.moveToWon);

**Current pattern to mirror exactly:**

**New actions** (per RESEARCH.md Pitfall 1 — single atomic `update()` call, never two sequential writes):
```typescript
moveToLost: async (dealId, category, note) => {
  const current = get().deals.find((d) => d.id === dealId);
  const patch = {
    ...fromPipelineGroup("lost", current?.pipelineStage),
    lostReason: note ? `${category}: ${note}` : category,
  };
  const updated = await dealsRepository.update(dealId, patch);
  set({ deals: get().deals.map((d) => (d.id === dealId ? updated : d)) });
},

moveToWon: async (dealId, terms) => {
  const current = get().deals.find((d) => d.id === dealId);
  const patch = { ...fromPipelineGroup("won", current?.pipelineStage), ...terms };
  const updated = await dealsRepository.update(dealId, patch);
  set({ deals: get().deals.map((d) => (d.id === dealId ? updated : d)) });
},
```
Add both to the `PipelineState` interface (lines 6-16) alongside `moveStage`'s signature. Do NOT widen `updateDeal`'s `Pick<...>` type (lines 12-15) to include `pipelineStage`/`outcome` — that would bypass `fromPipelineGroup`'s derivation invariant (RESEARCH.md Anti-Patterns).

**Error handling pattern:** `moveStage` itself does not try/catch (lets rejections bubble); `updateDeal` (lines 47-59) does catch+log+rethrow. Follow `updateDeal`'s stricter pattern for the new actions since they gate a multi-step UI flow where the caller needs to know about failures to avoid closing the popover/dialog on error.

## Shared Patterns

### Zustand store — atomic single-write action shape
**Source:** `src/features/pipeline/store/pipelineStore.ts` lines 39-45 (`moveStage`)
**Apply to:** `moveToLost`, `moveToWon` — compute one full patch object, call `dealsRepository.update()` exactly once, replace deal by id (never by index) in `set()`. Never chain two sequential store/repository calls for a single user-perceived action (RESEARCH.md Pitfall 1).

### react-hook-form + zod + shadcn Field composition
**Source:** `src/features/pipeline/components/AddDealDialog.tsx` lines 147-217 (per-field `Controller`/`Field`/`FieldLabel`/`FieldError` block)
**Apply to:** `LostReasonPopover.tsx`, `WonContractTermsDialog.tsx` — every form field follows the same `Controller` render-prop shape: `Field data-invalid={fieldState.invalid}` wraps `FieldLabel` + input/`Select`, followed by conditional `FieldError`.

### Dialog/Popover dismiss vs. submit must never share a store-mutating path
**Source:** RESEARCH.md Pitfall 2, derived from `AddDealDialog.tsx` lines 113-128 (`onSubmit` vs. `handleOpenChange`)
**Apply to:** `LostReasonPopover.tsx`, `WonContractTermsDialog.tsx` — the Radix-driven `onOpenChange` (Escape/click-away) must only clear local `pendingGroup` state in `StageSelect`, never call `moveToLost`/`moveToWon`. Only the form's own `onSubmit` handler calls the store action and then closes.

### shadcn/ui primitive wrapper convention
**Source:** `src/components/ui/dialog.tsx`, `src/components/ui/select.tsx` (both read this session)
**Apply to:** new `src/components/ui/popover.tsx` — `import { cn } from "cn"`, `import { X as XPrimitive } from "radix-ui"` (single meta-package import, not `@radix-ui/react-popover` directly), `data-slot="..."` attributes on every exported sub-component, Portal-wrapped Content.

### Pure derivation function extension
**Source:** `src/shared/utils/pipeline-group.ts` (full file)
**Apply to:** Adding `"won"` requires touching exactly this one file's two functions — any new code elsewhere that checks `deal.outcome`/`deal.pipelineStage` directly to determine display group duplicates this source of truth and must not be written (RESEARCH.md "Don't Hand-Roll" key insight).
