# Phase 3 — UI Design Contract

> Visual and interaction contract for the Deal Terms Wizard (2-step Add Deal modal, DEAL-06).
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | shadcn (already initialized — `components.json` present) |
| Preset | `radix-nova` — base color `neutral`, CSS variables on, no class prefix |
| Component library | Radix UI primitives (via shadcn, `radix-ui` package) |
| Icon library | lucide-react |
| Font | `Geist Variable` (`@fontsource-variable/geist`), fallback `sans-serif` |

No new shadcn components are pulled this phase. The wizard is built entirely from primitives already generated in `src/components/ui/`: `dialog`, `field`, `input`, `label`, `select`, `button`, `separator`. Per 03-CONTEXT.md's Claude's Discretion note, no radio/switch/checkbox/stepper primitive exists yet and none is added — Prorata (yes/no) and the step indicator are both built from existing primitives (Select for Prorata; plain text/dots for the step indicator), matching the "follow the existing shadcn Dialog visual pattern already established in `AddDealDialog.tsx`" instruction.

---

## Visual Hierarchy / Focal Point

| Step | Focal Point |
|------|-------------|
| Step 1 | The first input field (Deal Name) is the focal point — it receives autofocus on dialog open, sits directly under the "Step 1 of 2" indicator with no competing accent-colored elements above it, and the "Next" button is the only accent-colored control on the step, anchoring the eye's path from top field to bottom-right CTA. |
| Step 2 | The "Create Deal" button is the focal point — as the terminal action of the wizard it is the only accent-colored element competing with the 5 input fields above it; fields use neutral borders/labels so the eye travels top-to-bottom through Prorata → Grace Period → Contract Term → Frequency → Currency and lands on the accent-colored submit control bottom-right, consistent with Step 1's single-accent-per-screen rule. |

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, step-dot gaps |
| sm | 8px | Step indicator row gap, compact control spacing |
| md | 16px | Default field spacing, dialog content padding (`DialogContent p-4`) |
| lg | 24px | Not used this phase (no section-level breaks inside a 2-step modal) |
| xl | 32px | Not used this phase |
| 2xl | 48px | Not used this phase |
| 3xl | 64px | Not used this phase |

Exceptions: the reused shadcn primitives keep their built-in Tailwind spacing values, which are not strict multiples of 4 (e.g. `FieldGroup`'s `gap-5` = 20px, `Button`'s `gap-1.5` = 6px, `DialogContent`'s `p-4`/`gap-4` = 16px). These are **not** modified this phase — only new wizard-specific chrome (the step indicator, the inter-step transition wrapper, the Back/Next/Create button row) must follow the 8-point scale above: step-dot gap = `sm`(8px), step content top margin = `md`(16px).

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 (normal) | 1.5 (`leading-normal`) — field descriptions, error messages, select option text |
| Label | 14px (`text-sm`) | 500 (medium) | 1.0 (`leading-none`) — `FieldLabel`/`Label`, matches existing `AddDealDialog` fields |
| Heading | 16px (`text-base`) | 500 (medium) | 1.0 (`leading-none`) — `DialogTitle` ("Add Deal") and the step indicator text ("Step 1 of 2" / "Step 2 of 2: Deal Terms") |
| Display | Not applicable this phase | — | — | No display-level text exists inside a modal wizard; largest text is the Heading role above. |

Exactly 2 weights (400, 500) and 3 sizes (14px, 16px, plus 12px only if a step-dot numeral label is added — default to unlabeled dots per Claude's Discretion, so 2 sizes are actually used: 14px, 16px). Matches every existing dialog/field primitive already in the codebase — no new type scale introduced.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--background` (`oklch(1 0 0)`, white) | Dialog surface (`DialogContent` uses `--popover`, effectively the same near-white) |
| Secondary (30%) | `--muted` / `--secondary` (`oklch(0.97 0 0)`) | `DialogFooter` background (`bg-muted/50`), inactive step dot |
| Accent (10%) | `--primary` (`oklch(0.205 0 0)`, near-black) | Reserved for: the "Next" button (step 1 → step 2), the "Create Deal" button (final submit), the active/current step dot, and focus-visible rings on inputs/selects (`--ring`) |
| Destructive | `--destructive` (`oklch(0.577 0.245 27.325)`) | Field-level validation error state only (invalid border/ring on `Input`/`Select`, `FieldError` text). This phase has no delete/destroy action — destructive is scoped exclusively to required-field validation errors on Step 2's 5 new fields. |

Accent reserved for: **Next button, Create Deal button, active step indicator dot, focus-visible ring on the currently-focused field.** Back and Cancel are `variant="outline"`/neutral — never accent-colored, so the primary path (Next/Create) stays visually distinct from the secondary paths (Back/Cancel), consistent with `AddDealDialog.tsx`'s existing single accent-colored submit button.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (step 1) | "Next" — advances to Step 2, preserving Step 1 values (D-01, D-02) |
| Primary CTA (step 2, final) | "Create Deal" — submits the full 7-field payload via the existing `addDeal()` store action |
| Secondary action (step 2) | "Back" — returns to Step 1 with all values preserved (D-02) |
| Cancel action (either step) | "Cancel Add Deal" — closes the wizard entirely, discarding all entered values immediately, no confirmation dialog (behavior matches existing `AddDealDialog.handleOpenChange` — resets and closes on any dismissal — but the label itself names the action being cancelled rather than reusing the generic "Cancel" wording) |
| Empty state | Not applicable — this is a creation-only form, not a data list; both steps render with default/empty field values until the user types (no separate "empty state" UI beyond ordinary unfilled inputs) |
| Empty state body | N/A (see above) |
| Error state (per-field) | Reuses the established `FieldError` pattern, e.g. "Grace period is required", "Contract term is required", "Frequency is required", "Currency is required", "Prorata is required" — same tone/format as existing `addDealSchema` messages ("Name is required", "Value must be positive") |
| Destructive confirmation | Not applicable — no destructive action exists in this wizard (Cancel is a neutral dismiss, not a destructive one; matches existing Add Deal modal, which has no confirm-on-close) |

## UI Considerations

Applicable state considerations resolved: 4 covered, 1 backstop, 1 unresolved — 2 categories not applicable (no list-collection element exists in this phase; the wizard is a single-record creation form, not a data list).

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | Wizard form (step 1 + step 2) | ✅ covered | Both steps render with default/empty field values until the user types — no special empty-state UI needed for a creation-only form (see Copywriting Contract "Empty state" row) |
| partial | Wizard form (step 1 + step 2) | ✅ covered | Zod schema requires all 5 step-2 fields (D-09); Next/Create submission is blocked and per-field `FieldError` messages render for any incomplete field, matching the established `AddDealDialog` pattern (see Copywriting Contract "Error state" row) |
| overflow | Frequency/Currency `Select` dropdown | ✅ covered | Option labels are short, fixed English words ("Quadrimestral" being the longest) rendered in the existing shadcn `SelectContent`, which already wraps/scrolls per its built-in primitive — no custom truncation needed |
| long-text | Step indicator label ("Step 1 of 2" / "Step 2 of 2 — Deal Terms") | ✅ covered | Fixed, short, static string — no user-generated or variable-length content, no truncation risk |
| loading | "Create Deal" submit (interactive-control) | 🧪 backstop | No submit-in-flight spinner/disabled state is added this phase — matches Phase 1's documented gap (STATE.md: "no double-submit guard on Add Deal"). Held out as a backstop: if a future phase adds async latency to `addDeal()`, this wizard's Create button must be revisited. |
| error | "Create Deal" submit (interactive-control) | ⚠ unresolved | `addDeal()`'s promise is not caught in the existing `AddDealDialog` pattern; this wizard reuses the same call site. Planner assumption: no submit-failure UI this phase, consistent with existing behavior — revisit when the mock repository is swapped for a fallible network implementation (see STATE.md Blockers). |

*(`populated` / `zero-one-many` do not apply — no list-collection element exists in this phase.)*
